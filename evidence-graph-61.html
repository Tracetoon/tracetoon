Pull-request descriptions judges prefer, for 39% less

Tracetoon writes pull-request descriptions from the session logs your AI coding agent already keeps. Its evidence graph, built per PR in the embedded Relate database, gives the writing model a compact, cited brief instead of raw logs. On 61 real pull requests, judges preferred the graph-written description to Tracetoon's original multi-agent workflow 64 times to 38 on Codex, at 39% lower cost. On Claude Code it matched the original's quality at 28% lower cost.

What Tracetoon does

AI coding agents such as Claude Code and Codex keep session logs on disk: the requests you typed, the plans they made, every file edit and every command they ran. A pull-request description written from the diff alone loses most of that. It can't say why the change was made, what was tried first, or which tests ran on the final code.

Tracetoon is an open-source agent skill that writes the description from that record. When your agent is about to open a PR, Tracetoon finds the sessions that produced the branch, pulls a redacted evidence set from them (private paths and secrets removed), and has the agent draft from it. It then checks the draft: every factual sentence has to trace back to evidence, and the Validation section is generated from recorded test and build runs rather than typed by the model. You approve the result before anything is posted.

What the evidence graph changes

Tracetoon's original workflow was already careful. Separate agents research the repository's rules, draft the description from a digest of the logs, and independently review every claim, so no agent checks its own work. That is accurate but expensive: an expensive model has to rediscover the structure of the change from text, working out which commit sentence describes which hunk, which functions are new and why the change was made, and then a second instance does it all again to check the first.

The evidence graph moves that rediscovery out of the model. One command reads the session logs and git, builds a small graph in Relate (an embedded graph database written in Rust, shipped inside Tracetoon's CLI as WebAssembly), runs a fixed set of Cypher queries, and prints a compact brief. No model is involved, so this step costs no tokens. The writer gets short tables it can cite (which request led to which code, which function owns each behavior, which test ran after the last edit) instead of rereading everything.

Quality: judges prefer the graph PRs on Codex, and it matches on Claude Code

Each description was compared head to head with the original workflow's description of the same change. Two judges per provider read both, in both orders, against an expert-reviewed fact sheet and the original evidence, and picked the one a maintainer would rather receive. Points on a 100-point score are an arbitrary scale, so we lead with the judges' choices.

Codex (GPT-6.1 Terra)

  • When both judges agreed, they picked the graph PR 64 times to 38 (63%).
  • Each judge alone also preferred it: GPT-6.1 Terra 63%, GPT-6.1 Sol 59%.
  • It conveyed 82% of each change's key facts, against 72%.

Claude Code (Sonnet 5.5)

  • The stronger judge, Opus 5.5, preferred the graph PR 107 times to 58 (65%). The Sonnet 5.5 judge split evenly (56–56).
  • When both judges agreed: 54–46, not a significant difference. We count this as equal quality.
  • Fewer factual errors per draft after expert checking: 0.58 vs 0.78.

The score lead

The benchmark's composite score (claims, context, uncertainties and a reviewer rubric, minus penalties for errors) tells the same story. The charts show only the range where the two workflows differ.

Cost: 39% less on Codex, 28% less on Claude Code

The graph replaces work the model used to do with a deterministic build step, and the drafting and review steps read a short brief instead of the full logs.

This addresses CI failures and stalled test processes while making PR publication work from forks.

The GitHub target is resolved from a matching gh default remote or origin, and carried through context, doctor, PR lookups and publication. Render records the target and shows it in the preview; if a target was recorded, publication stops if the target has changed. When the origin owner differs from the target owner, the PR head identifies that owner and existing PR lookup filters by it. If origin is absent, the gh default can supply the target. Check receipts are also read without task bookkeeping, summary selection accounts for wrapper totals, and receipt identity excludes temporary-directory and terminal variables while retaining PATH.

The test runner bounds each file, allows a grace period after a completed summary, and uses the summary result if the process must be killed after that period. Bun receives a 120-second per-test timeout; the workflow sets a 45-minute job timeout. The CLI flushes output and exits explicitly; a test guard can use its recorded exit code when a completed CLI process remains alive. Review tests redirect output to files and bound CLI calls. tests/flow.test.ts covers target use and changed-target rejection; tests/target.test.ts covers target selection and fork heads. tests/receipts-and-fork.test.ts covers fork heads and receipts, while tests/spawn-guard.test.ts and tests/test-files.test.ts cover process exit, hangs and summaries. Review tests cover CLI calls and concurrent pass ordering. The bundled artifact and build identity are updated.

How we tested

The cases

  • 61 real pull requests from 12 repositories: Tracetoon (17), AI First CLI (10), prbench (9), Showtail (6), AI First content (4), VEX AIM agent (4), AI First website (3), VEX AIM workshop (3), VEX V5 serial (1), WinApps (2), AI First extension (1), Bazzite login (1).
  • Each comes with the original agent session logs that produced it: 33 from Claude Code, 28 from Codex.
  • Each has an expert-reviewed fact sheet: the claims a good description should convey, the context a reviewer needs, what the evidence does not establish, and plausible-but-wrong traps. Sheets were drafted from the diff and logs, reviewed by a six-model panel (three Claude Opus 5.5, three GPT-6.1 Sol), and disputes were settled by debates judged by Fable 5.1 and GPT-6 Astra.

The runs

  • Both workflows wrote every PR three times with the same model, prompt and sandbox. They differ only in the installed Tracetoon skill.
  • Two judges per provider (Codex: GPT-6.1 Sol and Terra; Claude: Opus 5.5 and Sonnet 5.5), each in both orders, fixed before the run.
  • Every factual error a judge flagged was checked against the evidence by Fable 5.1 and GPT-6 Astra (Fable settles disagreements): 422 flags, none left unresolved.
  • Run with the open prbench harness under its confirmation protocol.

Run details and disclosures

Our own adoption gate. Before the run we fixed four criteria per provider: the score's lower 95% bound at least −2.5, factual errors not worse by more than 0.05 per PR, cost at most 0.8×, and claim coverage not lower by more than 0.05. Claude Code met all four. Codex met three. Its expert-confirmed errors were lower (0.18 vs 0.23 per PR), but the 95% interval of the difference reaches +0.098, above our 0.05 margin, so the strict non-inferiority test is not met. With about 0.2 errors per PR, many more cases would be needed to narrow that interval.

  • No held-out set. All 61 cases form one pool used both to tune Tracetoon and to evaluate it. Earlier, a sealed held-out split was used once; that run found errors (statements that no request or test was recorded) which the current build fixes. We then chose a larger single pool over repeated small held-out sets.
  • Judges disagree often. Agreement between the two judges was 64% (Cohen's κ 0.44) on Codex and 56% (κ 0.39) on Claude Code. On Claude Code the Opus judge favored the graph and the Sonnet judge did not, so we report Claude Code as equal quality. The Codex judges include GPT-6.1 Terra, the same model as the Codex writer in both workflows.
  • Uncertainties on Claude Code. Graph drafts on Claude Code respected fewer of the fact sheets' uncertainties (53% vs 67%). This is the main open quality gap.
  • Wall time. On Claude Code the graph workflow took about 1.8× as long per PR; on Codex it was about the same (1.05×).
  • Sandbox validation. Writers ran tests in an offline sandbox. 31 of 61 cases' test suites pass there at the PR's final commit; the rest fail for host reasons or have no test command. Both workflows saw the same environment.
  • Smaller cost gain than our first test. An earlier 5-PR comparison measured 3.3× (Codex) and 2.3× (Claude Code) cheaper. Since then the graph workflow gained a review pass and fresh checks to fix accuracy, which cost tokens. The quality picture held: +2.9 then, +2.7 now on Codex, with a much tighter interval.
  • Models and versions. Writers: GPT-6.1 Terra (medium effort) in the Codex CLI and Claude Sonnet 5.5 (medium) in Claude Code 2.1.319. Tracetoon build candidate53 (Tracetoon 532372d); baseline is Tracetoon's original multi-agent workflow. Harness: prbench bench-v4 f4f7139, confirmation protocol, 61 cases x 3 replicates.
